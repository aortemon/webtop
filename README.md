# WebTop

Web-система мониторинга ресурсов систем ОС в реальном времени

## Описание

Приложение предоставляет web-интерфейс для мониторинга ресурсов /proc-based
операционных систем. Программа собирает данные о нагруженности системы,
анализирует и агрегирует их, предоставляет REST API бекенд и WebUI фронтенд для
их просмотра в браузере.

## Требования

### Системные требования

- **ОС**: на базе ядра Linux 4.9+

- **ФС**: procfs, смонтированная в /proc

- **Сеть**: доступ в интернет (для получения `Chart.js` от CDN и
  `nlohmann::json` из GH-репозитория )

### Инструменты сборки

- **Компилятор**: GCC 10+ / Clang 12+

- **Система сборки**: CMake 3.24+

### Опционально

- **Node.js 16+** (если требуется перекомпиляция фронтенд-скриптов)

- **TypeScript 4+** (если требуется перекомпиляция фронтенд-скриптов)

## Подготовка и запуск

### 1. Сборка

Чтобы собрать приложение, в корне проекта выполните следующие команды:

```bash
mkdir build
cd build
cmake ..
cmake --build .
```

Исполняемый файл будет доступен по пути `./build/src/webtop`.

Для фронтенда используются TypeScript скрипты: они предварительно
транспилированы в JavaScript, но, при желании, процедуру можно повторить,
выполнив команду `npx tsc ./static/js/*.ts` в корне проекта.

### 2. Настройка

В файле `.env` содержатся некоторые настройки проекта:

- `ENABLE_COLORED_OUTPUT` - флаг для включения/отключения цветного вывода логов
  с помощью escape-последовательностей. `1` - чтобы включить, любое прочее
  значение отключает выделение цветом. По умолчанию =`1`.

- `ENABLE_DEBUG_INFO` - флаг для включения/отключения логгирования
  debug-информации в консоль (события ppoll, установление соединения/отправке
  SSE пакетов, ...). `1` - чтобы включить, любое другое значение отключает вывод
  debug логов. По умолчанию =`0`.

- `LISTEN_PORT` - порт на котором нужно запустить сервер. По умолчанию `8080`.

- `STATIC_DIR` - папка, содержащая статические файлы фронтенда. Путь указывается
  относительно корневой директории проекта.

- `COMMON_STATS_UPDATE_RATE` - интервал обновления дашборда с общей информацией
  в секундах. По умолчанию =`1`. Только натуральные числа.

- `PROCS_STATS_UPDATE_RATE` - интервал обновления списка процессов в секундах.
  По умолчанию =`1`. Только натуральные числа.

> В текущем проекте реализован только один вариант фронтенда, поэтому изменение
> `STATIC_DIR` не имеет смысла. Все остальные настройки могут быть изменены на
> усмотрение пользователя.

### 3. Запуск

Для запуска приложения, в корне проекта выполните команду

```bash
./build/src/webtop
```

Сервер будет прослушивать все сетевые интерфейсы на указанном в `.env` порту,
либо сообщит об ошибке, которая не позволяет серверу запуститься.

## Ключевые моменты

- **Модульность**: проект разделён на независимые модули `util`, `logger`,
  `reader`, `aggregator`, `server`

- **Парсинг /proc**: все системные метрики читаются напрямую из файлов procfs
  Linux.

- **RAII-управление**: `ScopeGuard` обеспечивает автоматическую очистку
  ресурсов.

- **Потокобезопасность**: логгер, анализаторы и SSE-соединения защищены
  мьютексами.

- **Данные в реальном времени**: сервер отдаёт метрики через SSE-соединение.

- **Веб-интерфейс**: две страницы (дашборд и процессы) с графиками Chart.js и
  сортируемой таблицей.

## Выбранные решения

### Сериализация через `nlohmann/json`

- **Альтернатива**: самописная сериализация через ручное формирование строк
- **Почему выбран**: библиотека header-only, автоматическая обработка
  экранирования и вложенных структур, установка на этапе сборки через CMake

### Обход /proc c помощью `dirent`

- **Альтернатива**: `std::filesystem::directory_iterator`
- **Почему выбран**: `dirent` позволяет считывать содержимое директорий с
  помощью одного системного вызова. `std::filesystem` требует несколько
  системных вызовов на каждую директорию/файл, что значительно снижает скорость
  приложения, особенно при маленьких интервалах обновления состояния ресурсов
  системы

### Servet Sent Event

- **Альтернатива**: polling
- **Почему выбран**: уменьшение нагрузки на сервер (нет лишних запросов);
  доставка данных в реальном времени без задержки опроса; автоматическое
  переподключение через `EventSource`; одно долгое соединение вместо множества
  коротких; меньший трафик; независимость фронтенда от параметров запуска
  приложения
